# The Claude workflows, through Workload Identity Federation

**2026-11-24.** The Claude GitHub app's setup adds two workflows: `claude.yml`, which answers `@claude` on issues, comments and reviews, and `claude-code-review.yml`, which reviews each pull request. As the app writes them, both read a stored `ANTHROPIC_API_KEY` secret, ask for more than `contents: read`, pin actions to tags and leave the token in the checkout, so the workflow lockdown refused them. Spec 0006 lets the two files in with no secret, under an exact allow-list of their own, the way `codeql.yml` has one. The work counts as sensitive (authentication): the security pair reads the spec and the diff at Test, the session's own pick, logged on the issue.

## What was built (PACT-101)

- **The two workflows.** Each run trades the job's GitHub OIDC token (audience `https://api.anthropic.com`) for a short-lived Anthropic token through Workload Identity Federation. The files carry the federation rule, organization and service account IDs, which are identifiers, not credentials. The rule, which lives in the Claude Console, is the control: it matches the repository owner's account, the subject prefix, the audience and an allow-list of actor accounts. Each job's guard (an owner, member or collaborator, or one of the owner's three agent apps by login; for `claude.yml`, `@claude` in the text; for the review job, a head branch of this repo) is defence in depth. The job token reads and holds `id-token: write`, nothing else; the action's writes go through the app's installation token, and `main`'s ruleset with no bypass actor keeps them off `main`.
- **The owner's three agent apps may start a run** (an owner's decision, relayed in chat after the first push). Each file sets `allowed_bots` to exactly the three apps' names, written without the `[bot]` suffix: the pinned action lowercases both sides and strips the suffix before it compares (`src/github/validation/actor.ts` at the pinned commit), and an unlisted bot actor is refused. The guard admits an author whose login is one of the three `[bot]` logins beside the association check. The gate holds both exactly; `*`, another bot or another login is refused. (`gate/tests/workflow.test.mjs`). `claudeProblems` holds each file to the keys, values, permissions, guard, pins and action inputs spec 0006 W3 and W4 name. Values held exactly: the name, the triggers with their event types, each job's permission set, the guard text, the runner, and every action input but the three federation IDs. Those IDs are held to the shape of their kind (`fdrl_`, `svac_`, a UUID). Checkout's pin must equal `gate.yml`'s. `folderProblems` hands exactly these two file names to it; every other file, a copy of either one included, keeps the common lockdown, which refuses the `id-token` grant.
- **The bad cases.** One per refusal, in the style of the CodeQL allow-list's table, each plant asserted to change the text and to be caught by its message, run against both files where the refusal applies to both. A folder-level case shows a third file that copies either workflow under another name is refused, and that a job or check named for a gate job is refused in the two files too.
- **The threat model.** "Code that runs" names the four workflows and the two Claude files' allow-list, and adds three accepted residuals: a run that an allowed actor, or a session holding an app key, starts reads text from anyone, spends Anthropic tokens, and can steer what Claude writes through the app's token, short of `main`; the review plugin is fetched unpinned at run time; a branch an allowed actor pushes can change the files and mint an Anthropic token in its run, since the rule bounds who, not what.
